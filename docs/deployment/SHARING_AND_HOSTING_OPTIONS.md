# Sharing and hosting MoMo-FDVS

**Verified:** 2026-08-23  
**Scope:** Source transfer, local Docker execution, temporary sharing boundaries, managed hosting choices and native-app distribution.

## 1. What the current Docker setup provides

The repository contains four cooperating services:

1. PostgreSQL database;
2. Flask API, OCR and private receipt storage;
3. React administrator portal;
4. Expo/React Native application exported for the web.

Docker Compose keeps these services and their supported runtimes together. It does not, by itself, create a public internet link. A URL containing `localhost` works only on the computer running Docker. A private LAN address works only while that computer is running and the other device can reach the same network.

## 2. Give the complete app to another person to run locally

Use one of these source packages:

- the GitHub repository and the exact reviewed branch; or
- the deterministic academic submission ZIP generated by `scripts/build_submission_package.py`.

Do not send the current `.env`, PostgreSQL volume, private receipt volume, tokens, passwords or real receipt images. The recipient should create fresh local credentials and an independent database.

The recipient needs Docker Desktop with Docker Compose. From the repository root, the established local path is:

```powershell
py -3.12 scripts\bootstrap.py
npm.cmd --prefix apps\mobile ci
npm.cmd --prefix apps\mobile run build:web

$env:POSTGRES_PORT="55436"
$env:API_PORT="8003"
$env:ADMIN_PORT="5177"
$env:MOBILE_WEB_PORT="8084"
$env:CORS_ALLOWED_ORIGINS="http://localhost:5177,http://localhost:8084"

docker compose -p momo-fdvs-demo up -d --build db api admin mobile
docker compose -p momo-fdvs-demo ps
```

On a new database, they can run the development-only idempotent seed command documented in `docs/LOCAL_RUN_GUIDE.md`, replacing every example email and password with their own local test values. The seed is blocked in production, hashes passwords with Argon2, assigns the staff roles and requires an initial password change.

The resulting local URLs are:

- mobile/web: `http://localhost:8084`;
- administrator portal: `http://localhost:5177`;
- API health: `http://localhost:8003/api/v1/health`.

This is the most reproducible way to hand over the complete current prototype. Docker's production guidance also describes a single Docker server as the simplest Compose deployment and recommends a production-specific override file for ports, logging, environment variables and restart behavior: [Docker Compose production guidance](https://docs.docker.com/compose/how-tos/production/).

## 3. Can a link be sent instead?

Only after one of these is true:

- the other person is on the same network and uses the Docker computer's LAN address;
- the system is deployed to an internet-accessible host; or
- a temporary secure tunnel is deliberately configured.

Do not expose this development stack casually through router port forwarding or a public tunnel. The system accepts private financial screenshots and has local-development defaults. Public access requires HTTPS, production secrets, strict CORS origins, persistent private storage, backups and production-safe administrator provisioning.

## 4. Hosting choices

### Option A — Linux VPS with Docker Compose (closest to the current app)

This requires the fewest architectural changes. Rent an Ubuntu server, install Docker Engine and Compose, copy or clone the repository, create a production-only environment file on the server, and run the four services behind an HTTPS reverse proxy. A DigitalOcean Droplet is one example of a Linux virtual server: [DigitalOcean Droplet quickstart](https://docs.digitalocean.com/products/droplets/getting-started/quickstart/). AWS Lightsail is another VPS-oriented option with compute, storage, networking, DNS and snapshots: [Amazon Lightsail overview](https://docs.aws.amazon.com/lightsail/latest/userguide/what-is-amazon-lightsail.html).

Advantages:

- current Compose topology transfers with minimal change;
- Docker volumes and Tesseract remain under one operator's control;
- one domain can route `/api`, the mobile web app and the administrator portal.

Trade-offs:

- the owner must patch the server, configure a firewall, HTTPS, monitoring and backups;
- database and private receipt storage recovery remain the owner's responsibility;
- a single server is suitable for a controlled demonstration, not automatic high availability.

### Option B — Railway (managed demonstration deployment)

Railway documents how each Compose service maps to a separate Railway service. It recommends managed PostgreSQL, supports Dockerfile builds, private networking and persistent volumes: [Railway Docker Compose deployment guide](https://docs.railway.com/guides/docker-compose), [Railway data and storage](https://docs.railway.com/data-storage).

For this repository, that means:

- one managed PostgreSQL service;
- one API Docker service with a private persistent volume mounted at `/app/.local/private-storage`;
- separate administrator and mobile-web services;
- private service-to-service database networking;
- public domains only for the intended web/API entry points.

Railway does not execute this repository's Compose topology as one unchanged runtime. Service dependencies, variables, health checks, migrations and volume mounts must be translated and verified.

### Option C — Render (managed services with a persistent disk)

Render can build services from Dockerfiles, provides managed PostgreSQL and supports persistent disks: [Render Docker deployments](https://render.com/docs/docker), [Render persistent disks](https://render.com/docs/disks), [Render PostgreSQL](https://render.com/docs/postgresql).

For this repository, deploy the API, administrator frontend and mobile web frontend as separate services. Attach a paid persistent disk to the API's private receipt-storage path, or implement the planned object-storage adapter. Render's default filesystem is ephemeral, so uploaded receipts would be lost without a disk or external object storage. A disk is attached to a single instance and disables zero-downtime deployments, which matters when judging the trade-off.

## 5. Recommended path

For a supervisor, classmate or examiner who wants to run the entire project independently, send the repository-safe ZIP plus `docs/LOCAL_RUN_GUIDE.md` and let them run Docker locally.

For a short controlled public demonstration, use a small Linux VPS because it matches the current Compose design most closely. Use Railway if managed PostgreSQL and a web dashboard are more important than preserving Compose unchanged.

Do not call either deployment production-ready until production secrets, HTTPS, backups/restore, monitoring, privacy retention and native-device acceptance have been completed and evidenced.

## 6. Sharing an installable phone app

The currently accepted mobile evidence is the Expo web export, not an App Store or Play Store build. Expo EAS can create internal-distribution build URLs, but an iOS ad-hoc build is restricted to registered device identifiers and the mobile build still needs a publicly hosted API: [Expo internal distribution](https://docs.expo.dev/build/internal-distribution/). Store distribution is a separate signed submission workflow: [Expo distribution overview](https://docs.expo.dev/distribution/introduction/).

Therefore, distributing a native binary does not distribute the complete system. The API, PostgreSQL database and private receipt storage still need to run locally or be hosted securely.
